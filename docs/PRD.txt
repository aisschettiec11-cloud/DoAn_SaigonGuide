PRD – Hệ thống Thuyết minh tự động đa ngôn ngữ theo GPS (TP.HCM Audio Guide)
Môn học: Công nghệ phần mềm  |  Nhóm: 3 thành viên  |  Phiên bản: 1.0  |  Ngày: 23/10/2026
1. Giới thiệu tài liệu
1.1 Mục đích
Tài liệu Product Requirements Document (PRD) này mô tả đầy đủ bối cảnh, mục tiêu, yêu cầu chức năng, yêu cầu phi chức năng, kiến trúc kỹ thuật và thiết kế dữ liệu của hệ thống TP.HCM Audio Guide – ứng dụng web thuyết minh tự động đa ngôn ngữ dựa trên định vị GPS cho du khách tại 6 điểm tham quan nổi tiếng của TP. Hồ Chí Minh. Tài liệu là cơ sở để nhóm lập trình, kiểm thử và đưa trực tiếp vào tài liệu thuyết minh đồ án.
1.2 Phạm vi
Hệ thống gồm: (1) ứng dụng web cho du khách (mobile-first), (2) trang quản trị nội dung (Admin CMS), (3) Backend REST API theo kiến trúc 3 lớp, (4) cơ sở dữ liệu MySQL, (5) quy trình CI/CD.

	2. Bối cảnh và vấn đề
TP.HCM đón hàng triệu lượt khách quốc tế mỗi năm đến từ Hàn Quốc, Nhật Bản, Trung Quốc, Thái Lan, châu Âu, Mỹ... Khu vực trung tâm (Quận 1) tập trung nhiều di tích như Nhà thờ Đức Bà, Bưu điện Trung tâm, Dinh Độc Lập, Chợ Bến Thành. Hiện tại du khách gặp các khó khăn:
* Rào cản ngôn ngữ: biển chỉ dẫn thường chỉ có tiếng Việt – Anh, thiếu tiếng Hàn, Nhật, Trung, Thái.
* Chi phí và tính linh hoạt: thuê hướng dẫn viên tốn kém, bị phụ thuộc lịch trình đoàn; thiết bị audio guide truyền thống phải thuê, bấm số thủ công.
* Thông tin phân mảnh: du khách phải tự tra cứu trên mạng, nội dung không thống nhất, đôi khi sai lệch.
* Thiếu trải nghiệm theo ngữ cảnh: thông tin không xuất hiện đúng lúc, đúng nơi du khách đang đứng.
Giải pháp đề xuất: một ứng dụng web chạy trực tiếp trên trình duyệt điện thoại, không cần cài đặt; du khách chọn ngôn ngữ, bật định vị; khi bước vào vùng geofence của một điểm tham quan, hệ thống tự động hiển thị thông tin và phát giọng thuyết minh bằng đúng ngôn ngữ đã chọn.
3. Mục tiêu sản phẩm và chỉ số thành công
3.1 Mục tiêu
1. Tự động kích hoạt thuyết minh khi du khách tới đúng vị trí GPS của 6 điểm.
2. Hỗ trợ tối thiểu 6 ngôn ngữ: Việt, Anh, Hàn, Nhật, Trung (giản thể), Thái; kiến trúc cho phép thêm ngôn ngữ mới mà không sửa mã nguồn.
3. Hiển thị bản đồ trực quan, vị trí hiện tại, vị trí 6 điểm và đường đi.
4. Cho phép quản trị viên quản lý địa điểm, nội dung, ngôn ngữ, audio.
5. Đáp ứng yêu cầu môn học: kiến trúc 3 lớp, CI/CD, tài liệu UML đầy đủ.

	5. Phạm vi sản phẩm
5.1 Trong phạm vi (In scope)
* Web app du khách: chọn ngôn ngữ, bản đồ, định vị, tự động thuyết minh, phát/tạm dừng/tua audio, xem chi tiết điểm.

* Admin CMS: đăng nhập, quản lý POI, ngôn ngữ, bản dịch, audio, xem thống kê lượt nghe.
* REST API, CSDL MySQL, CI/CD.
5.2 Ngoài phạm vi (Out of scope)
* Ứng dụng native iOS/Android; thanh toán; đặt tour; chế độ offline hoàn toàn; nhận diện hình ảnh; chatbot.

9.2 Thuật toán phát hiện geofence
Khoảng cách giữa vị trí (φ1, λ1) và POI (φ2, λ2) tính bằng Haversine, R = 6371000 m:
a = sin²(Δφ/2) + cos φ1 · cos φ2 · sin²(Δλ/2);  d = 2R · atan2(√a, √(1−a))
POI được coi là "đang ở trong" khi d ≤ radius_m. Để tránh nhiễu GPS, áp dụng:
* Hysteresis: vào vùng ở bán kính R, chỉ coi là rời vùng khi d > 1,3R.
* Debounce: vị trí phải nằm trong vùng liên tục ≥ 2 lần cập nhật (khoảng 3–5 giây) mới kích hoạt.
* Lọc độ chính xác: bỏ mẫu có coords.accuracy > 50 m.
9.3 Quy tắc xử lý nhiều điểm và phát lặp
* Nếu nhiều POI cùng chứa vị trí: chọn POI có d/radius nhỏ nhất; ưu tiên theo trường priority.
* Cooldown mặc định 30 phút cho mỗi POI trong một phiên; người dùng có thể bấm "Nghe lại".
* Đang phát POI A mà vào vùng POI B: hỏi người dùng "Chuyển sang B?" thay vì cắt ngang.
9.4 Chiến lược đa ngôn ngữ
1. Nội dung gốc tiếng Việt do nhóm biên soạn, kiểm chứng từ nguồn chính thống.
2. Bản dịch lưu sẵn trong bảng location_translations (không dịch realtime để đảm bảo tốc độ và chi phí).
3. Dịch tự động bằng dịch vụ dịch máy ở Admin, bắt buộc có bước duyệt trước khi xuất bản.
4. Audio: sinh trước bằng TTS, lưu file (mp3) và cache; dự phòng speechSynthesis của trình duyệt với lang tương ứng (vi-VN, en-US, ko-KR, ja-JP, zh-CN, th-TH).
5. Thêm ngôn ngữ mới chỉ cần thêm bản ghi languages và nhập nội dung – không sửa mã.
6. Chuỗi giao diện (nút, nhãn) dùng i18n (react-i18next) với file JSON theo ngôn ngữ.
10. Yêu cầu phi chức năng
Nhóm
	Yêu cầu
	Hiệu năng
	API p95 ≤ 500 ms; trang tải ban đầu ≤ 3 s trên 4G; audio bắt đầu ≤ 2 s
	Độ tin cậy
	Uptime mục tiêu 99% giai đoạn demo; xử lý lỗi thống nhất, không crash khi mất GPS/mạng
	Bảo mật
	HTTPS bắt buộc (Geolocation API chỉ chạy trên HTTPS); JWT + băm mật khẩu BCrypt; tham số hoá truy vấn (EF Core) chống SQL Injection; CORS whitelist; rate limiting; không lưu dữ liệu định danh du khách
	Quyền riêng tư
	Chỉ gửi toạ độ khi cần; không lưu lịch sử toạ độ chi tiết, chỉ lưu log lượt nghe ẩn danh (session id ngẫu nhiên)
	Khả dụng
	Mobile-first, nút lớn, hỗ trợ trình duyệt Chrome/Safari/Edge bản mới; đạt tiêu chí WCAG AA cơ bản về tương phản
	Khả năng mở rộng

	11.2 Kiến trúc 3 lớp của Backend
* Presentation Layer (API): Controllers, DTO, middleware (xác thực JWT, xử lý lỗi, logging). Chỉ nhận request, validate, gọi Service, trả response.
* Business Logic Layer (BLL): Services chứa nghiệp vụ: GeofenceService, NarrationService, TranslationService, AudioService, AuthService, StatisticsService.
* Data Access Layer (DAL): Repository + AppDbContext (EF Core), Entities, Migrations. Mọi truy cập MySQL đi qua lớp này.
Quy tắc phụ thuộc một chiều: Presentation → BLL → DAL; các lớp giao tiếp qua interface (DIP), tiêm phụ thuộc bằng DI container.

12. Thiết kế cơ sở dữ liệu
12.1 ERD
Sơ đồ ERD ngay bên dưới. Quan hệ chính: một Location có nhiều LocationTranslation; một Language có nhiều LocationTranslation; một LocationTranslation có tối đa một AudioNarration (hoặc nhiều phiên bản); PlayLog tham chiếu Location và Language; Feedback tham chiếu Location.
 ERD · 7 bảng, 7 quan hệ 

ERD · 7 bảng, 7 quan hệ
Sơ đồ chỉ liệt kê các cột khóa và cột quan trọng; đầy đủ cột xem từ điển dữ liệu bên dưới. Mỗi cặp (địa điểm, ngôn ngữ) có đúng một dòng trong location_translations, nên thêm ngôn ngữ mới chỉ là thêm dữ liệu.
12.2 Từ điển dữ liệu
admin_users: id (PK), username (unique), password_hash, full_name, role (Admin/Editor), created_at, is_active.
languages: id (PK), code (unique, vd: vi, en, ko, ja, zh, th), name, native_name, tts_voice_code (vd: ko-KR), is_default, is_active.
locations: id (PK), slug (unique), latitude DECIMAL(9,6), longitude DECIMAL(9,6), radius_m INT, priority INT, image_url, opening_hours, address, display_order, is_active, created_at, updated_at.
location_translations: id (PK), location_id (FK), language_id (FK), name, short_description, narration_text (TEXT), history_text (TEXT), status (Draft/Published), is_machine_translated, updated_at; ràng buộc unique (location_id, language_id).
audio_narrations: id (PK), translation_id (FK), file_url, duration_sec, source (TTS/Upload), created_at.
play_logs: id (PK), session_id (CHAR 36), location_id (FK), language_id (FK), trigger_type (GPS/Manual), played_at, completed (bool).
feedbacks: id (PK), location_id (FK), rating (1–5), comment, language_id (FK), created_at.
Chỉ mục: locations(is_active, display_order), location_translations(location_id, language_id) unique, play_logs(location_id, played_at). Toàn bộ bảng dùng charset utf8mb4, collation utf8mb4_unicode_ci.

15. CI/CD
15.1 Quy trình Git
Nhánh main (ổn định), develop (tích hợp), feature/*. Pull Request bắt buộc có ít nhất 1 reviewer và CI xanh mới được merge. Commit theo Conventional Commits.
15.2 Pipeline CI (GitHub Actions – kích hoạt khi push/PR)
1. Checkout mã nguồn.
2. Backend: dotnet restore → dotnet build → dotnet test (kèm báo cáo coverage).
3. Frontend: npm ci → npm run lint → npm test → npm run build.
4. Phân tích chất lượng (analyzer/SonarCloud, tuỳ chọn).
5. Build Docker image cho API và Frontend.
15.3 Pipeline CD (khi merge vào main)
1. Đẩy image lên registry (GitHub Container Registry).
2. SSH vào máy chủ, docker compose pull && docker compose up -d.
3. Chạy migration EF Core, kiểm tra health check /health.
4. Lỗi → rollback về image trước đó.
Bí mật (chuỗi kết nối DB, khoá API dịch/TTS, JWT secret) lưu trong GitHub Secrets, không đưa vào mã nguồn.
